fio-vault · VPS-Strategie

Der Token fließt links.
Die KI sitzt rechts.
Die Linie wird nie überquert.

Zwei Dinge, die du verstehen willst: was %no-protection bei einem GPG-Schlüssel wirklich bedeutet — und den genauen Weg, den ein Secret nimmt, ohne dass die KI ihn je zu sehen bekommt. Kein Marketing, nur der Mechanismus.

01

Was %no-protection heißt

Ein GPG-Schlüssel ist eine Datei. Diese Datei kann selbst mit einer Passphrase verschlüsselt sein — oder eben nicht. %no-protection ist die GPG-Anweisung beim Erzeugen: „lege den privaten Schlüssel unverschlüsselt ab“. Es ist nicht dasselbe wie eine leere Passphrase.

🔐 Standard — heute

Schlüssel mit Passphrase

Der private Schlüssel liegt selbst verschlüsselt auf der Platte. Um ihn zu benutzen, muss GPG erst die Passphrase haben — über pinentry (ein Eingabefenster) oder FIO_VAULT_PASSPHRASE.

  • ✗ Headless ohne TTY: pinentry findet kein Terminal → hängt / schlägt fehl
  • ✗ Workaround: Passphrase irgendwo hinterlegen (env, Datei, Agent) — neues leakbares Artefakt
  • ✓ Schützt eine Off-Box-Kopie des Schlüssels
gpg --gen-key: Key-Type: RSA Passphrase: mein-geheimnis # ← Schlüssel wird hiermit verschlüsselt %commit
🔓 Opt-in — für den VPS

Schlüssel ohne Passphrase

Der private Schlüssel liegt im Klartext auf der Platte. GPG braucht nichts zu entsperren — es entschlüsselt sofort. Kein pinentry, kein Terminal, keine env-Variable.

  • ✓ Headless ohne TTY: entschlüsselt sofort, exit 0
  • ✓ Nichts im Environment, das die KI finden könnte
  • ✗ Eine Off-Box-Kopie des Schlüssels ist sofort nutzbar → Dateirechte sind jetzt die Grenze
gpg --gen-key: Key-Type: RSA %no-protection # ← keine Passphrase-Zeile %commit
Die Falle, die du vermeidest FIO_VAULT_PASSPHRASE="" (leerer String) ist NICHT das hier. Im Code ist die Prüfung if (passphrase) — ein leerer String ist falsy, fällt also still auf den Agent-Pfad zurück. Du denkst „keine Passphrase“, änderst aber nur den Code-Pfad. Der ehrliche Weg ist ein Schlüssel ohne Passphrase, kein leerer Passphrase-String.
02

Bringt die Passphrase auf dem VPS Sicherheit?

Auf einem Single-User-VPS liegen Ciphertext, privater Schlüssel und jede Passphrase-Quelle unter derselben UID. Die ehrliche Frage ist: gegen wen hilft die Passphrase dann noch?

Angreifer / SzenarioHilft die Passphrase?Warum
KI als gleicher User (versehentlich) ✗ Theater Die KI läuft als der Vault-User — sie liest den Schlüssel und die Passphrase ohnehin. Das ist genau der Fall, den fio-vault adressiert.
Bösartiger gleicher User — außer Scope Braucht eine OS-Grenze (eigener User). Explizit als Non-Goal dokumentiert — eine Passphrase ändert daran nichts.
Gestohlenes Backup / Disk-Image ✓ Echt Eine Off-Box-Kopie des Schlüssels ist mit Passphrase wertlos, ohne sofort nutzbar. Der einzige echte Verlust — operativ mitigiert (Backup-Hygiene).
Versehentlicher git push von vault.key ✓ Echt Gleiche Logik. Deshalb: vault.key nie committen, und --no-passphrase bleibt opt-in mit lautem Warnhinweis.
Fazit Die These „die Passphrase bringt auf dem System keine zusätzliche Sicherheit“ ist wahr — eng gefasst auf einen Same-User-Leser auf einer Single-User-Box. Eine Passphrase wird erst dann echt, wenn ein Mensch sie interaktiv tippt, damit ein unbeaufsichtigter Prozess den Schlüssel nicht nutzen kann. Genau dieses Szenario existiert auf einem unbeaufsichtigten VPS nicht — das ist dein ganzer Punkt.

Der Flow: wo berührt die KI den Token?

Zwei Tiers. Beide halten den Wert von der KI fern. Der Unterschied ist, ob die KI den Namen des Secrets tippen muss. Folge dem orangenen Pfad — er ist der Token-Wert, und er überquert nie in die violette KI-Zone.

04

So sieht das in der Praxis aus

Derselbe Token-Abruf, drei Wege. Achte darauf, was nach dem Befehl im Terminal zurückkommt — das ist alles, was auch die KI sieht.

vps · zsh
# ✅ Tier 1 — die KI nennt nichts Sensibles vps$ bun run sync ↳ synced 412 records in 1.8s ✓ # ✅ Tier 2 — Name sichtbar, Wert nicht vps$ fio-vault exec --only apify-token -- bun scripts/sync.ts ↳ synced 412 records in 1.8s ✓ # ❌ Verbannt — der Roh-Wert fließt durch die KI vps$ fio-vault get apify-token ✗ refusing to print a raw secret to a non-TTY (exit 3) → use: fio-vault exec --only apify-token -- <cmd>
05

Das Setup auf dem VPS

Sechs Schritte. Nach Schritt 1 ist die Passphrase-Friktion weg; ab Schritt 2 sind die Dateirechte deine Sicherheitsgrenze — das ist jetzt Pflicht, nicht optional.

1

Schlüssel ohne Passphrase anlegen

fio-vault init --no-passphrase erzeugt einen %no-protection-Schlüssel. Bei bestehendem Vault: Passphrase einmalig auf leer ändern und vault.key neu exportieren — kein Re-Encrypt der Secrets nötig.

2

Dateirechte sperren — DAS ist jetzt die Grenze

chmod 600 vault/vault.key · chmod 700 ~/.gnupg · alles im Besitz des einen Deploy-Users. Ist die Box nicht echt Single-User → stopp, nimm stattdessen einen eigenen OS-User.

3

Nichts ins Environment setzen

Jedes export FIO_VAULT_PASSPHRASE=… aus ~/.zshrc, systemd Environment= und cron-Headern entfernen. Die Abwesenheit ist der ganze Punkt.

4

Entry-Points auf Wrapper verdrahten

Pro wiederkehrendem Task ein package.json-Script oder bin/*-Wrapper, der loadSecrets() aufruft. Die KI ruft den Namen — nicht den Schlüssel.

5

Backup-Hygiene (der eine echte Verlust)

vault.key und ~/.gnupg aus jedem Off-Site-Backup ausschließen oder separat verschlüsseln. Nie committen — nur *.gpg + manifest.json + .gpg-id.

6

Unbeaufsichtigt smoke-testen

Aus einem Non-TTY-Kontext: ssh vps 'fio-vault exec -- node -e "process.exit(process.env.SOME_KEY?0:1)"' → erwartet exit 0, kein Prompt, kein Hang.
